# 职业熟练度与自创技能设计

状态：2026-11-08 用户确认实施，首版已接入。当前实现、限制与验证以 [ForAI/Business/CustomSkills.md](../ForAI/Business/CustomSkills.md) 为准；本文保留设计依据与后续扩展方向。

首版实际开放10个主体与8种修饰；采用均分熟练度、每10次完整收益升一级、11级精通、一个主体加两个修饰槽。仅正式战斗使用增长熟练度；探索与部署计数未接入。

## 已确认方向

- 职业拥有各自的熟练度与等级；按用户“超过十”的表述，精通门槛为职业等级 11。
- 使用某职业技能，增长对应职业熟练度；可以同时培养多个职业，不改为按角色经验增长当前职业。
- 精通职业后，可以使用该职业已经学会的技能来自创技能。
- 自创方式为从已学技能提取招式、属性或附加效果，在兼容范围内自由组合。
- 精通多个职业后，可以跨这些职业组合。

## 设计时的实现基线

建议补齐职业成长，并对技能定义、查询和机制分派做渐进改造。现有目标检查、命中、伤害、Buff、资源消费和表现框架继续复用。

| 已核实事实 | 对方案的影响 |
| --- | --- |
| `CharacterGrowthData` 只有角色等级、经验、已加入职业、当前职业和整数技能 ID 集合，没有职业等级 | 新增按职业保存的成长状态，不能复用角色等级字段 |
| `ProfessionSkillTable.minLevel` 当前是角色等级门槛 | 新增职业等级不应顺带改变旧课程门槛；课程升级体系若要调整，应单独决定 |
| 一个技能可以出现在多个职业的课程中，骑士、法师与奥术骑士存在共享课程 | 熟练度归属与自创素材授权必须有明确规则，不能用图鉴主分类推断 |
| `CombatSkillTable.proficiency` 指剑术、法杖等二级属性 | 它不是职业熟练度，不修改其原有语义 |
| `CombatSkillTable` 已提供目标、范围、弹道、效果序列、消耗等结构 | 可从现有定义提取可组合部分，但不是所有字段都能任意互换 |
| 法师通过 `SpellRecipeTable` 从可用技能集合自动展开固定组合，包含装备授予来源 | 保留这种固定法术；自创素材另查永久已学资格，不直接使用战斗可用技能集合 |
| 装备、职业机制、Tips、图标和特效仍大量依赖配置技能 ID | 只拼 `effectIds` 或临时塞一个 ID 无法完成自创技能接入 |
| `Battle:ObserveSkillUse` 在成功命令后发出一次 `skill_used`，涵盖多目标与借机攻击入口 | 可复用其一次提交边界；探索使用和部署的计数范围仍要明确接入 |

## 已采纳规则与扩展方向

### 职业成长

1. 已加入职业从 1 级开始，各自积累熟练度；达到 11 级自动精通，切换职业不清除成长或精通资格。
2. 角色总等级、属性点、被动点、研习机会维持现有职责；职业升级先只服务于精通，不重复赠送这些奖励。
3. 正常提交一次符合来源资格的职业技能，记一次熟练度。合法攻击未命中仍计入；取消、校验失败、预览、GM 授予和被动周期伤害不计入。多目标、多发、多个效果不会把一次使用重复计数。
4. 首版建议资格为“永久已学的职业课程或初始赠送课程”。仅装备、坐骑临时授予的技能不提供职业熟练度；普通攻击只有明确登记为职业训练动作时才计入。
5. **共享课程建议均分**：同一技能属于角色已加入的多个职业时，固定总收益在这些职业间均分，不因多加入职业增加收益总量；与当前职业无关。用整数细分单位及余数状态保存，不通过浮点累积，也不能每次截断丢失收益。
6. 自创技能按保存的素材职业来源分配同一次使用的总收益。重复职业合并，每个不同来源职业均分；两种职业各得一半，三种职业各得三分之一。素材越多不增加总收益。
7. 职业等级经验曲线、单次收益、等级上限都配表。建议首版将精通作为主要成长终点，暂不额外设计精通后的等级奖励；数值需结合战斗频率确定。
8. 战斗、反应攻击、部署和探索行为需逐项登记合法计数入口。建议首版支持已经接入统一提交事件的战斗行为；探索施工、准备技能另接真实提交入口后开放，不能因只接战斗而把某职业永久排除。是否允许纯练习刷熟练度、是否加入重复衰减，实施前一并确定。

### 素材资格与保存

- 素材必须同时满足：角色永久掌握源技能、该源技能属于一个已精通职业、该技能显式开放了对应的可组合部分。
- 同一个共享技能只解锁一份相同素材；只要有一个归属职业已精通即可使用。保存组合时记录采用哪个已精通职业作为来源，避免读档或切职改变归属。
- 自动开放的法术组合、职业变体与特殊传授技能不因“当前可施放”自动成为素材；需要明确的持有与职业归属适配。首版可先开放课程中的基础技能。
- 创造不消耗源技能，不额外消耗现有研习机会；创建、改名和编辑只在探索阶段进行。建议先不引入金币、随机失败或额外研究货币。
- 成品归角色本人保存，切职后仍可使用；武器、触媒、弹药、材料和状态前提仍按成品要求检查。首版不自动开放传授、装备交易或 NPC 随机生成。
- 不把自创成品继续拆成新素材，避免循环合成和递归加成；玩家可编辑原配方。

### 组合结构

建议首版采用 **一个主体招式 + 最多两个修饰部分**。可以同职业组合，也可以来自两到三个已精通职业；数据结构不把来源职业数量固定为两个。

| 组成 | 决定内容 | 约束 |
| --- | --- | --- |
| 主体招式 | 目标类型、动作、距离、范围形态、命中方式、基础结算及武器要求 | 整个技能只有一套主要目标选择流程 |
| 属性修饰 | 伤害类型、元素表现、对应资源与触媒要求 | 不把另一技能的完整基础伤害重复叠加 |
| 效果修饰 | 命中附加状态、破甲、击退等已适配能力 | 声明触发阶段、接收者、次数、互斥标签和成本 |

每个源技能显式列出可提取部分。例如一门火球术可以开放火焰属性、燃烧效果，但不自动把它的射程、范围、伤害和地面区域全部打包送入剑术。

修饰槽不要求一格属性、一格效果；兼容规则决定可选组合。同一功能不能重复叠加，互斥元素和目标规则在编辑时给出具体原因。

### 示例（设计示意，非现有成品）

| 精通职业与已学来源 | 选择内容 | 成品行为 |
| --- | --- | --- |
| 战士：破势一击 + 破甲猛击 | 破势一击主体 + 破甲部分 | 一次近战攻击附带破甲，重新计算伤害、AP 与冷却 |
| 骑士 + 法师：裂阵斩 + 爆裂火球 | 裂阵斩主体 + 火焰属性 | 保留斩击目标与范围，火焰部分引入施法资源与触媒条件 |
| 两个以上已精通职业 | 主体 + 元素修饰 + 兼容状态修饰 | 一次动作内结算，按实际素材职业分配熟练度 |

这些示例不授权绕过现有触媒专精。剑术加入法术部分后仍须有合法武器与触媒搭配；装备要求无法同时满足时，界面应显示原因。

## 平衡与执行边界

- **创建时给出完整预览**：效果、目标、命中、伤害系数、AP、施法点、冷却、材料和装备要求；不让玩家任意填写伤害数值。
- 用模块成本、兼容标签和硬性边界共同限制组合。范围、多发、控制、位移的收益不能仅按附加伤害线性计价；首版只开放已有明确预算的组合族。
- 保留一个基础攻击预算。多目标或多发必须重新分配附加效果预算，并为控制类效果声明每动作或每目标触发次数，不能默认每发完整叠加。
- 武器和魔法混合技能需要分别记录其伤害来源和属性缩放，避免对同一部分重复应用武器与法术加成。资源需求也独立表达，不能仅靠单一 `skillGroup` 推断全部成本。
- 校验来源、目标、状态、全部资源和落点之后，一次性提交消耗；非法组合或失败命令零消耗，合法未命中正常付费。组合执行不能依次调用多次完整 `TrySkill`。
- 冷却归稳定的自创技能身份；编辑只在无战斗状态进行。对相同配方的复制设置同一冷却族，避免改名或复制绕过冷却。
- 被动计数、观摩、发现和职业经验都保留一次行动语义；具体效果在自己的触发阶段执行，不能把每个片段当作又施放了一次源技能。
- 复杂机制逐个开放。首版优先直接攻击、伤害类型与常规 Buff；缴械、身体部位选择、位移、地表区域、召唤、施工和伙伴指令需专门适配，不能仅根据配置存在就暴露为可拼素材。

## 技能系统改造

### 统一定义与身份

引入统一技能定义查询边界：普通技能读取静态表，自创技能读取角色配方并编译为相同的运行时描述。查询结果只读，随后按现有顺序应用装备、天赋、状态等修正。

建议区分静态技能引用与自创技能引用：静态引用含配置 ID，自创引用含角色 ID 与该角色内稳定的作品 ID。保留旧整数调用的静态适配入口；首版为兼容现有整数命令，使用角色作用域的独立运行时句柄，并由统一定义入口解析；不向静态配置表插入作品行。

配方保存版本、稳定身份、源技能、素材标识、采用的职业来源、选择参数及自定义名称。只保存可验证的定义，不保存一份已经吃过装备加成的技能快照；缓存随配方或规则版本失效。

### 组件与机制

- 拆出“基础定义 → 组合校验与编译 → 装备/属性修正 → 行动准备 → 一次提交 → 各阶段效果”的清晰边界。
- 第一批素材声明兼容目标、攻击载体、触发时机、接收者与消耗。无法表达的旧机制继续使用原实现，待适配后才对自创开放。
- 职业、法术的静态机制表目前多按 ID 查找；新运行时描述应携带已解析的机制与资源要求，让通用执行读取描述。不要把所有旧机制一次重写，也不要让新技能绕过它们的资源检查。
- 旧固定法术组合继续保留。后续可以共享素材或效果实现，但其自动解锁规则仍独立于职业精通。

### 数据与持久化

- C# 权威状态负责职业熟练度、余数与等级，以及角色自创技能集合；Lua 负责配置规则、校验、编译和只读投影，不保存第二份权威状态。
- 在既有角色存档中添加版本迁移。旧档没有职业使用记录，不能根据角色等级伪造各职业经历；建议已加入职业初始化为 1 级、零熟练度，补偿策略如需要再确认。
- 读档严格校验作品身份、素材来源、重复组件和版本。需要迁移的配方明确迁移，已移除素材的作品显示失效原因并允许修复；不静默删除或替换成其他效果。

### 界面与表现

- 职业徽记增加等级、进度和精通标识；角色手记增加自创入口。
- 编辑页选择角色后，展示可用主体与修饰、槽位、实时效果/成本及不兼容原因；保存后出现在该角色的已学能力和战斗栏。
- 公共图鉴保留静态技能目录；角色作品另设个人目录，不要求把每件作品生成到 `SkillAtlasTable`。
- Tips 从运行时描述与完整本地化模板生成。自动名称、槽位名、限制原因使用配置 `text` 或语言表；玩家输入名称作为用户数据保存并转义富文本标记。
- 图标先由主体图标和元素/效果标识组合。动作取主体，粒子使用显式支持的组合表现；战斗快照传递足够的表现描述，不能让 C# 再按作品 ID 查询静态技能表。
- 新 UI 组件使用已保存的 LuaReference 绑定；资源接入仍按项目工具与 Editor 约束执行。

## 实施顺序与验收

1. 确定本稿待确认规则，尤其共享技能收益、有效使用范围、成长曲线与首版组合槽数。
2. 落地职业成长状态、来源映射、使用提交和存档；显示精通进度。定向检查 10/11 级边界、转职保留、共享技能分配、多目标只计一次及旧档迁移。
3. 建立统一技能查询与静态适配，先让原技能走同一入口。检查既有武器、法术、装备资源和 Tips 行为无变化。
4. 用少量已明确开放的主体/修饰形成完整闭环：同职业组合、跨职业组合、保存/读档、战斗栏、真实执行和表现。
5. 定向覆盖资格拒绝、互斥组合、混合资源一次扣费、未命中、控制触发次数、重复配方冷却、版本迁移与本地化。后续按机制族扩充素材，不把全技能一次迁移作为首版前提。

首版交付验证见当前模块文档；本轮完成离线规则、真实C#状态与战斗、原生UI、存档迁移和本地化检查，未进入Play。
